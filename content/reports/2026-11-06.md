### 1-1 OpenAI「GPT‑6 Cyber」

<callout icon="📌" color="gray_bg">
<b>何が新しいか</b>

OpenAIが、認可された範囲内で脆弱性の発見と検証に特化したモデル<b>「GPT‑6 Cyber」</b>を公開した。ExploitGymは48.5%（前世代GPT‑5.6 Cyberは32.1%）。Linuxで948件の権限昇格エクスプロイト、Firefoxで未知の高深刻度81件を見つけたと公式に記している。
</callout>

#### なぜ重要か

- Preparedness Frameworkのサイバー区分を<b>HighからCritical</b>へ上げた。Daybreak Red経由で深い検証、Daybreak Blueで検証とパッチ支援を分けて提供する。
- スコープ外サービスの攻撃回避は、配備プロンプトなしで99.93%、ありで100%。境界を守る訓練を前面に出している。
- 当面は承認済みのDaybreak Red顧客向けAPI／Codexから。CiscoやCodeRabbitなどが利用を表明している。

#### どう使うか

1. 自社がDaybreakの対象か確認し、Red（深い検証）とBlue（トリアージ・パッチ）のどちらが必要か決める。
2. 既存の脆弱性管理フローに載せ、再現手順と候補パッチを人が必ず確認するルールを書く。
3. クリティカルインフラや本番への直接攻撃は禁止し、隔離環境とIP許可リストを前提にする。

- SIerが顧客向けペネトレーションの下準備をエージェントに任せ、人が再現と報告に集中する。

### 2-1 Cloudflare、Durable Object呼び出しの自動再試行

<callout icon="📌" color="gray_bg">
<b>何が新しいか</b>

Cloudflare Workersのランタイムが、Durable Objectへの`fetch()`とRPCで再試行可能な失敗を<b>自動で最大4回</b>リトライするようになった。初回開始から10秒を超える再試行は始めない。アプリ側の例外や`.overloaded`は対象外。
</callout>

#### なぜ重要か

- 短いネットワーク断で自前のリトライループを書かなくてもよくなる。
- 到達したかが不明な切断でも再送するが、先着が届いていればDO側が拒否し、<b>`retryable()`未指定なら二重実行しない</b>。
- 既存の自前リトライと重なると試行回数が増えるため、`maxRetries: 0`や自前回数の見直しが必要。

#### どう使うか

1. Wranglerを<b>4.158.0以上</b>に上げ、冪等なメソッドに`retryable()`を付ける。
2. stub取得時に`retry: { maxRetries, timeoutMs }`で上限を調整する（再試行0〜10、タイムアウト500〜60000ms）。
3. 加算など非冪等処理は`retryable()`を付けず、必要ならアプリ側でidempotency keyを持つ。

```js
import { DurableObject } from "cloudflare:workers";
import { retryable } from "cloudflare:durable-objects";

export class Cart extends DurableObject {
  static {
    retryable(this.prototype.setQuantity);
  }
  async setQuantity(itemId, quantity) {
    await this.ctx.storage.put(itemId, quantity);
  }
}
```

<callout icon="💼" color="green_bg">
<b>ビジネス活用例</b>

- カートやセッションDOを使うEC/BFFで、瞬間的なエッジ障害による失敗率をアプリ変更なしに下げる。
- 既存リトライ付きバッチWorkerは`maxRetries: 0`にし、二重課金リスクを避ける。
</callout>

### 3-1 IAM Roles AnywhereがCDPでCRL自動取得

<callout icon="📌" color="gray_bg">
<b>何が新しいか</b>

IAM Roles Anywhereが、証明書に埋め込まれた<b>CRL Distribution Point（CDP）</b>からCRLを自動取得・定期更新できるようになった。失効済み証明書の認証要求は拒否する。追加料金なしで全商用リージョン対象。
</callout>

#### なぜ重要か

- これまでCRLをRoles Anywhereへ手動インポートし、CA更新のたびに再投入が必要だった。
- AWS Private CAや自前PKIでも、公開到達可能なCDP URLがあれば使える。
- オンプレ／工場機器など証明書ベースの一時認証情報運用で、失効反映の遅延を減らせる。

#### どう使うか

1. 証明書にCDP URLが入っているか、Roles Anywhereの配布ポイント要件を満たすか確認する。
2. 信頼アンカーで自動失効チェックを有効化する（コンソール／SDK／CLI）。
3. 失効した証明書でAssumeが拒否されることをステージングで確認する。

<callout icon="💼" color="green_bg">
<b>ビジネス活用例</b>

- 工場や店舗の端末証明書運用で、CRL再インポート作業をやめ、失効の反映遅れによる不正アクセス窓口を狭める。
</callout>

### 5-1 OpenSSH 10.6p2／Alpine緊急修正（CVE-2026-123158）

<callout icon="📌" color="gray_bg">
<b>何が新しいか</b>

Portable OpenSSHが<b>10.6p2</b>を公開し、musl libcかつPAM無効のLinuxで起きるパスワード認証回避への回避策を入れた。Alpineも3.21.10／3.22.8／3.23.8／3.24.4などを同日公開し、`openssh-server`利用者に更新とsshd再起動を求めている。
</callout>

#### なぜ重要か

- パスワード欄が空のアカウントでも、長いパスワード入力で`crypt()`エラー値`*`と照合が一致し、<b>鍵専用のつもりでも侵入できる</b>ケースがある。
- コンテナや軽量VMでAlpine＋opensshがよく使われ、露出面が広い。
- すぐ上げられない場合は`PasswordAuthentication no`が公式の暫定策。

#### どう使うか

1. Alpine系ホスト／コンテナの`openssh-server`を固定版へ上げ、sshdを再起動する。
2. 上げられない間は`PasswordAuthentication no`にし、鍵認証のみにする。
3. 踏み台やCIランナーのベースイメージも同様に棚卸しする。

<callout icon="💼" color="green_bg">
<b>ビジネス活用例</b>

- 基盤チームがAlpineベースの踏み台・Bastion・開発用VMを当日パッチし、パスワード認証の残存を監査する。
</callout>

### 5-2 FrankenPHP 1.13.5で17件の脆弱性を修正

<callout icon="📌" color="gray_bg">
<b>何が新しいか</b>

FrankenPHPがセキュリティリリース<b>1.13.5</b>を出し、17件を修正した。最も重いのは`php_server`が<b>拡張子分割をすり抜けたアップロードをPHPとして実行</b>する問題（GHSA-j99q-3wr8-xj43）。同梱のCaddyは<b>2.11.9</b>へ上がり、FastCGIまわりの回避も含まれる。
</callout>

#### なぜ重要か

- ドキュメントルートへアップロードできるアプリでは、即RCEにつながる。
- オープンリダイレクト、HTTP/2 Hostなりすまし、パス規則バイパス、ワーカー間の出力混線なども同時修正。
- ワーカーモードで破壊的変更あり。リクエスト由来状態以外のリセット範囲が変わる。

#### どう使うか

1. FrankenPHPを1.13.5（Caddy 2.11.9）へ上げて再デプロイする。
2. アップロード先をドキュメントルート外へ移し、実行権限と拡張子チェックを見直す。
3. ワーカー利用時は`error_clear_last()`などが必要かアプリを確認する。

<callout icon="💼" color="green_bg">
<b>ビジネス活用例</b>

- PHP＋Caddy／FrankenPHPの公開サービスを当日パッチし、ファイルアップロード経路のペンテストを追加する。
</callout>

### 6-1 GitHubの新Gitストレージ「Rubicon」

<callout icon="📌" color="gray_bg">
<b>何が新しいか</b>

GitHubが、エージェント開発向けの新Gitストレージ構成（通称<b>Rubicon</b>）を詳しく解説した。オブジェクトはAzure Blob、参照更新は専用の合意サービスRef-CASに分け、<b>1リポジトリで数千書き込み/秒</b>・内部試験では5000並行エージェント／7200 push/秒を示した。限定プライベートプレビュー中。
</callout>

#### なぜ重要か

- Gitオブジェクトは内容アドレスで並列保存でき、合意が必要なのは参照更新だけ、という分離が設計の芯。
- 読み取り用の仮想レプリカと、コンパクション専用ノードを分け、メンテがリクエストCPUを食い潰さない。
- 自社のエージェント多数push前提のモノレポ設計や、Git互換ストレージの参考になる。

#### どう使うか

1. 「不変オブジェクト」と「参照のCAS」を分けているか、自社VCS／成果物ストアの設計を点検する。
2. バックグラウンド圧縮とオンライン経路を分離し、書き込み増加時のレイテンシ曲線を測る。
3. プレビュー参加が必要ならGitHubの案内を確認し、エージェントCIのpush頻度目標を再計算する。

### 8-1 Autobase 2.12

<callout icon="📌" color="gray_bg">
<b>何が新しいか</b>

自前インフラ向けPostgreSQL内部DBaaSのAutobaseが<b>2.12</b>を公開した。Netdata連携の組み込みダッシュボード、AWS／GCP／Azureでの<b>Multi-AZ既定配置</b>、AWS Secrets Manager連携、IMDSv2強制やEBS暗号化などのセキュリティ強化が入った。
</callout>

#### なぜ重要か

- マネージド相当の運用体験を自前に寄せる製品で、AZ障害耐性と秘密情報管理が標準に寄った。
- `PGPASSWORD`をやめパスワードファイルへ、ログからの秘密情報除去など、運用事故を減らす変更が多い。
- SSHジャンプホスト対応で、プライベート網のDBを踏み台経由管理できる。

#### どう使うか

1. 既存Autobaseクラスタのアップグレード手順とリリースノート差分を確認する。
2. 新規AWS構築ではMulti-AZとSecrets Manager／KMSを有効にし、IMDSv2を確認する。
3. デモsandbox（demo.autobase.tech）でダッシュボード項目を見て、監視要件と突合する。

<b>ビジネス活用例</b>

- オンプレ／自前クラウドにPostgreSQLを置くチームが、AZ分散と秘密情報の外部化を標準テンプレに入れる。
</callout>

### 9-1 GitHub Secret ScanningにSpaceX、検知精度も改善

<b>何が新しいか</b>

</callout>

#### なぜ重要か

- Starlink APIなど新しいクラウド／IoT系秘密のカバーが広がっている。

#### どう使うか

1. 組織でSecret Scanningとプッシュ保護が有効か確認する。
2. 既存のAWS／GCPキーアラートのノイズが減ったか、1週間分のトリアージ負荷を見る。
3. Starlinkや類似IoT APIキーのローテーション手順を秘密管理ランブックへ足す。
