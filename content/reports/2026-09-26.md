あわせて次の3つも発表された。
- Microsoft Copilot Managed Runtime（プレビュー）：Microsoft 365環境内でコードを安全に実行するホスティング基盤。サードパーティやプロ開発者にも開放される。
- Fabric IQ（Chat / CoworkでGA）：Power BIの2,000万以上のセマンティックモデルをCopilotの文脈に取り込む。
- プラグインレジストリ：Microsoft・パートナー・自社製のプラグインを一元管理する。
#### なぜ重要か
- エージェントの位置づけが「一時的に動くアシスタント」から「独自IDを持って常駐する同僚」に変わった。
- 課金が分かれた。日常的なAI利用はユーザーサブスクリプション（USL、固定費）、Cowork・Code・Autopilotや最先端モデルは使用量ベース課金（UBB）になる。
- Agent 365のコスト管理がCodeとManaged Runtimeにも広がる（Copilot Studioで作ったエージェントは10月対応予定）。管理者は支出ポリシー、クレジット申請の承認フロー、グループごとの利用可能モデルファミリーを設定できる。
- つまり導入時の主な論点は、どの機能を使うかよりも**コスト配賦と権限設計**になる。
#### どう使うか
1. Frontierプログラムへの参加状況を確認し、パイロット部門を決める。
2. Agent 365でモデルファミリーの制限と支出ポリシーを先に決める。この設定はAutoルーティングが選ぶモデルの範囲にも影響する。
3. プラグインレジストリで、IT部門が承認したプラグインだけを使える運用にする。
4. CodeやManaged Runtimeで作られる社内アプリについて、データ接続・共有範囲のガードレールを決めてから展開する。
<callout icon="💼" color="green_bg">

	- 経理部門の月次決算：Autopilotに「決算締め進行役」の役割を与え、スケジュールの逆算計画、各担当者への進捗確認、会議準備とフォローアップを任せる。経理担当は例外処理と判断に集中でき、締めにかかる日数の短縮を狙える。
	- 情シスの「シャドーIT吸収」計画：部門ごとに乱立するExcelマクロやAccess資産を、Code＋Managed Runtimeでテナント内アプリに置き換える。IT部門が統制できる基盤に集約し、UBBコストはAgent 365で部門別に配賦する。
</callout>

### 1-2 n8n、「Agents」を提供開始：ワークフローをツールとして使うエージェント
<callout icon="📌" color="gray_bg">
	**何が新しいか**
	ワークフロー自動化ツールのn8nが2026年9月25日、新しいエージェント機能「n8n Agents」を公開した。やってほしいことを自然言語で書き、モデルと使ってよいツール・ワークフローを選ぶだけでエージェントが動く。
</callout>
#### エージェントの構成要素
- モデル：手持ちの認証情報で使える任意のモデル、またはn8n Gatewayクレジット
- 指示：役割、口調、やってよいこと・いけないこと
- チャネル／トリガー：Slack、Telegram、Linear、Discord、スケジュール
- ツール：組み込み連携、MCPサーバー、任意のワークフロー
- Skills、サブエージェント、ナレッジ（csv / pdf / md / txtのアップロードはCloudで利用可。ベクトルストアにも対応）、メモリ、セッション
#### ガバナンス機能
- 機密性の高いツールには承認（Approve / Reject）を必須にでき、ツールごとに認証情報を割り当てられる。
- 下書き版と公開版を分けて管理できる。
- ワークフローからエージェントを呼び出す「Message an Agent」ノードが追加された。既存のAI Agentノードはそのまま使える。
#### なぜ重要か
- 中心の考え方は**ワークフローをツールとしてエージェントに渡す**こと。
- 公式の例では、CRMに「メモを追記するだけ」のワークフローを渡すので、エージェント自身はCRMへの書き込み権限を持たない。
- LLMの判断の柔軟さと、決まった手順の確実さを権限の境界で分けられる。最小権限をノーコードで実装できる現実的なパターンといえる。
#### どう使うか
1. 提供範囲を確認する：n8n Cloudの最新安定版では全ユーザーが使える。セルフホストは追加設定が必要で、Enterprise版は近日対応。現在はプレビュー段階。
2. Agentsタブ → Create Agent で作る。n8n Assistantに作りたいものを説明してもよい。
3. 公式の推奨どおり、社内でよく聞かれる1〜2システムにつないだSlackボットから始める。
4. 書き込み系の操作には必ず承認を付ける。
- 課金：エージェントの1ターンを1実行として数える。ワークフローやサブエージェントの呼び出しは別カウントせず、ワークフロー実行枠を共有する。
<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- SaaSのカスタマーサクセス：「アカウント情報取得」「アカウントへのメモ追記」「オンコール呼び出し（承認必須）」の3ワークフローだけを持つサポートエージェントをSlackに置く。一次対応と記録を自動化しつつ、エージェントにはCRMの鍵を渡さない。
	- 中小ECの朝会準備：毎朝のスケジュール実行で、前夜の注文・在庫アラート・問い合わせを要約してSlackに投稿する。1ターン＝1実行なのでコストを見積もりやすく、稟議も通しやすい。
</callout>

### 1-3 Exa、ディープリサーチの最上位モード「Exa Agent Ultra」を公開
<callout icon="📌" color="gray_bg">
	**何が新しいか**
	AI検索APIのExaが2026年9月25日、Exa Agentの最上位の処理レベル「Agent Ultra」を公開した。タスクをサブタスクに分けてサブエージェントに割り当て、数千の情報源をまたいで調査する。難しい部分には最先端モデルを、それで足りる部分には高速なモデルを使い分ける。
</callout>
- 網羅性と正確性が重要な「リスト作成」「エンティティ情報の補完（エンリッチメント）」向け。
- 手持ちの行を渡すと、それを除外して新しい候補だけを探せる。
#### なぜ重要か
- Exaが公表したベンチマーク（WANDR、DeepSearchQA、WideSearchなど）では、Opus 5.5、GPT-6 Astra、Perplexity Agentの最大設定を上回ったとしている。
- WANDRでは、Opus 5.5比+12.6%の品質を1タスクあたり半分のコストで出したとしている。
- ただし**評価はベンダー自身によるもの**で、採点にはgpt-6-lunaを判定モデルとして使っている。
- 「全件を洗い出す」調査は人手のコストが大きいので、評価用データを用意して自社で検証する価値はある。
#### どう使うか
1. 既存のExa Agentの処理レベルの1つとして使う。完全性がコストや速度より重要なタスクに向く。
2. 導入前に、正解が分かっている過去の調査（例：既知の競合リスト）で再現率・適合率・コストを測る。
3. 出典URLが付くので、人のレビューは裏取りに集中させる。
<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- VC・事業会社のM&Aチーム：「欧州で電池リサイクルを手がける全企業と、その創業者・調達額・顧客」といったマーケットマップの初稿を作らせる。アナリストは出典の検証と投資仮説づくりに時間を使える。
	- B2B営業のアカウントリスト作成：「病院に販売しているか」「データ基盤の責任者は誰か」など判断が必要な項目を引用付きで補完させる。既存のCRMの行を渡して重複を除き、新規ターゲットだけを毎月追加する。
</callout>

### 2-2 Cloudflare「Turnstile Spin」：コーディングエージェントがボット対策を正しく実装
<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Cloudflareは2026年9月25日のブログで「Turnstile Spin」を正式に紹介した。CAPTCHA代替の「Turnstile」の導入を、Claude Code、Cursor、Codexなど利用者のコーディングエージェント経由で最後まで完了させる仕組み。エージェントが該当コードを探して計画を示し、承認されるとフロントエンドのウィジェットとバックエンドのSiteverify検証をまとめて実装する。
</callout>
<callout icon="🗓️" color="blue_bg">
	Spin自体は7月からダッシュボードで提供済み。9/25は公式ブログで正式に紹介された日。
</callout>
#### 対応する3つのパターン
1. 新規導入
2. サーバー側検証が抜けているウィジェットの修復（ダッシュボードに「Fix with Spin」が表示される）
3. 他のCAPTCHAからの移行
#### なぜ重要か
- **ウィジェットを置いただけでサーバー側で検証していない状態**は、防御として機能していない。
- Cloudflareは各ウィジェットのSiteverify呼び出しを監視しているため、この典型的な実装漏れを検知して修正へ誘導できる。
- アプリケーションのコードはCloudflareに送られず、変更は手元のエージェントが承認後に行う。
- ブログによると、Turnstileは平日1日あたり約30億回の検証を処理している。Spinは7月の先行提供以降、6万5,000件以上のウィジェット作成に使われ、生成されたプロンプトは3万回以上コピーされた。
#### どう使うか
1. ダッシュボードのTurnstileページ、Wrangler、または公開スキルのURLをエージェントに貼り付けて起動する。
2. 公式が想定する組み合わせは、ダッシュボードから始めてスキルをエージェントに渡し、エージェントがWranglerで作業する形。
3. 既存サイトでは、まずダッシュボードに「Fix with Spin」が出ていないかを確認する。
- Turnstile自体は無料で、Cloudflareのプロキシを通していないサイトでも使える。

### 3-2 Cloudflare Workers：トレーシングのカスタムspan APIを拡張（OpenTelemetry互換）
<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Cloudflareは2026年9月25日、Workersのカスタムspanで使えるOpenTelemetryのspan APIを増やした。追加されたのは次の4つ。
</callout>
<table fit-page-width="true" header-row="true">
<tr>
<td>API</td>
<td>動作</td>
</tr>
<tr>
<td>`tracing.startSpan(name)`</td>
<td>アクティブにならないspanを作成して返す（`span.end()` で終了）</td>
</tr>
<tr>
<td>`tracing.getActiveSpan()`</td>
<td>現在アクティブなspanを返す。カスタムspanの外では、その呼び出しのルートspanを返す</td>
</tr>
<tr>
<td>`span.recordException(exception)`</td>
<td>spanに例外イベントを記録する</td>
</tr>
<tr>
<td>`span.setAttributes(attributes)`</td>
<td>属性をまとめて設定する。`setAttribute` / `setAttributes` はspanを返すのでメソッドチェーンが可能</td>
</tr>
</table>
#### なぜ重要か
- これまでspanオブジェクトを関数の引数で引き回す必要があった場面でも、**`getActiveSpan()`**** でヘルパー関数やライブラリの中から現在のspanに情報を付けられる**。
- エッジで動くアプリでも、ユーザー属性や例外をトレースに一貫して残せる。障害の切り分けとSLOの分析がしやすくなる。
#### どう使うか
公式の例：認証後にルートspanへ属性を付け、プロファイル取得をカスタムspanで囲む。
```typescript
import { tracing } from "cloudflare:workers";

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const user = await authenticate(request, env);
    // 呼び出しのルートspanに属性を付与
    tracing.getActiveSpan()?.setAttributes({
      "user.id": user.id,
      "user.plan": user.plan,
    });
    const span = tracing.startSpan("load-profile");
    try {
      return Response.json(await loadProfile(env, user.id));
    } catch (err) {
      span.recordException(err as Error);
      throw err;
    } finally {
      span.end();
    }
  },
};
```
<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- Workers上のSaaS：認証直後に `user.plan` などをルートspanに付け、有料プランの顧客だけのレイテンシやエラー率をOTelのバックエンドで切り出す。上位プラン向けのSLO監視とSLAレポートを自動化する。
	- 決済・外部API連携：外部呼び出しを `startSpan` で囲み、失敗時は `recordException` で記録する。障害時に「自社の問題か外部の問題か」を数分で判断できる体制を作り、一次回答までの時間を短くする。
</callout>
