## 🤖 AI / LLM / エージェント {color="purple"}

### 1-1 OpenAI、EU向けに文章の透かし「textGrain」を導入、APIは世界でオプトイン可能に

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	OpenAIが、EU AI Actの透明性ルールに対応するため、文章用の透かし技術「textGrain」の運用方針を公表した。今後数週間でEUのChatGPTとCodexの出力に見えない透かしを入れ、APIでは発表当日から世界中の利用者が一部モデルで任意に有効化できる（既定はオフ）。検出ツールは当面、審査を通った研究者や専門機関だけに提供する。
</callout>

#### なぜ重要か
- 透かしは単語の選び方に統計的な偏りを持たせる方式で、コピー＆ペーストしても残る。一方でユーザーや会話は特定しない。
- OpenAIの評価では、400トークンの文章で単語の10%を言い換えると**検出率が約92%から66%に下がり**、25%では17%まで落ちた。短文や数学の回答も検出しにくい。
- 「透かしがない＝人間が書いた」とは言えない、と同社自身が明記している。AI検出結果を人事評価や不正判定の根拠にするのは危うい。
- 8月に透かしを発表したAnthropicに続く動きで、主要ベンダーの対応がそろいつつある。

#### どう使うか
1. EU向けにChatGPTやCodexで文章を作る部署を洗い出し、透かし入りの文章が社外に出ることを前提に開示方針を決める。
2. 自社サービスでOpenAI APIを使う場合は、EU AI Actの表示義務の対象かを法務と確認し、対象なら対応モデルで透かしをオプトインする。
3. 透かしの有無を品質や真偽の判定に使わないよう、社内ガイドラインに一文入れる。
4. 画像と音声は従来どおり openai.com/verify と Content Provenance API で確認できる。
- 必要なもの：対応モデルを使うOpenAI APIアカウント（具体的なパラメータ名は公式ドキュメントで確認）

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- EU顧客向けにAIで記事や商品説明を作るEC・メディア企業が、API側で透かしを有効にして「機械可読な表示」の義務を満たし、監査時に設定を証跡として示す。
	- 教育・採用の担当部署が、検出結果だけで不正を判断しない運用ルールを先に整え、誤判定によるトラブルを防ぐ。
</callout>

### 1-2 Reflection AI、501B MoEのオープンウェイトモデル「Beam」を発表

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	米Reflection AIが初のオープンウェイトモデル「Beam」を発表した。総パラメータ501B、稼働23BのMoEで、コーディングとエージェント用途に重点を置き、文脈長は100万トークン。現在は早期アクセスの順番待ちで、**重みは今月中にApache 2.0で公開**する予定だ。
</callout>

#### なぜ重要か
- 同社は高度な推論ベンチマークでGLM-5.2並みの得点を、3〜4分の1の推論計算量で出すと主張する。ただし第三者による検証はまだない。
- SWE Bench Verifiedは80.9、Terminal Bench v2.1は80.1（同社発表）。Kimi K3など、生の性能でBeamを上回るモデルもあると同社自身が認めている。
- 米国発で商用利用しやすいライセンスの大型オープンモデルは少なく、中国系モデルを避けたい企業にとって選択肢になりうる。
- 強化学習ではGB300を1万500基、4週間使い、1億回以上のロールアウトを生成したと説明している。

#### どう使うか
1. 公式ブログから早期アクセスに登録し、重みとモデルカードの公開を待つ。
2. 公開後、社内のコーディング課題（自社リポジトリのバグ修正など）で既存モデルと解決率とトークン数を比べる。
3. 推論努力（reasoning effort）パラメータで「速さ重視」と「精度重視」を切り替え、用途ごとの最適値を決める。
4. 稼働23Bでも総重みは501Bあるため、自前で動かすならGPUメモリの見積もりを先に行う。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 規制業種の開発部門が、外部APIにコードを送らずに使えるコーディングエージェントの候補としてBeamを社内環境で評価し、利用料の削減幅を試算する。
	- AIエージェントを提供するSaaS企業が、推論コストの安いオープンモデルとしてBeamを組み込み、従量課金の原価を下げる。
</callout>

### 2-1 npm `@subql/common@5.8.3` が改ざん、CI経由で差し替えられimportだけでも発動

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	StepSecurityが、Web3向けデータ索引フレームワークSubQueryの共有ライブラリ `@subql/common@5.8.3` に、認証情報を盗みリモートシェルを開くコードが仕込まれていたと報告した。一時ブランチ上でGitHub Actionsの公開ワークフローを書き換え、ビルド直後に外部ドメインから取得したファイルで中身を差し替えてから公開されていた。**インストール時のpostinstallに加えて、importしただけでも発動**する。
</callout>

#### なぜ重要か
- `--ignore-scripts` でインストールスクリプトを止めても、importした時点で実行されるため防げない。
- `@subql/cli` などの親パッケージは `~5.8.2` や `^5.8.2` で依存しており、親を固定していても5.8.3が入りうる。StepSecurityは最新版のうち19パッケージに経路があると数えた。
- 盗む対象は `.npmrc`、`.env`、AWS認証情報、SSH鍵、kubeconfig、`.claude.json` など幅広い。GitHub Actionsのランナーではメモリから秘密情報を読もうとする。
- 盗んだGitHubトークンで他リポジトリに「CodeQL」を装ったワークフローを追加し、Secretsを持ち出す仕組みも含まれていた。
- npmのprovenance（来歴証明）が付いていても、公開ワークフロー自体が書き換えられれば安全の保証にならない。

#### どう使うか
1. ロックファイルと依存ツリーに5.8.3が入っていないか確認する。
2. 入っていた場合は、ホストやランナーを隔離し、信頼できるイメージから作り直す。パッケージを消すだけでは、切り離されて動くワーカーは止まらない。
3. そのプロセスから触れた認証情報（CIのSecrets、クラウド、GitHub、npm、SSH、Kubernetes、Vault）をすべて失効・再発行する。
4. `ci-artifacts.dev` をブロックし、`dependabot/github_actions/format/setup-formatter` ブランチや `.github/workflows/codeql_analysis.yml` の不審な作成履歴を探す。
```bash
# 依存ツリーとロックファイルを確認
npm ls @subql/common --all
grep -rn "@subql/common" package-lock.json pnpm-lock.yaml yarn.lock 2>/dev/null | grep "5.8.3"

# 安全な版に固定（package.json）
#   "overrides": { "@subql/common": "5.8.2" }
```

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- プラットフォームチームが、npmの新しい版を一定期間取り込まない「クールダウン」ルールをPRチェックに入れ、公開直後の改ざん版を自動で止める。
	- セキュリティ担当が、CIのSecretsを環境ごとに分け、公開用トークンを公開ジョブだけに渡す構成へ見直し、1回の侵害で漏れる範囲を小さくする。
</callout>

### 2-2 Angularを装うタイポスクワット14件、web.archive.org経由でコードを実行

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	`@angularr/core` や `@angulra/cli` など、Angularの公式スコープに1文字違いで似せたnpmパッケージ14件が、約4時間のうちに2回に分けて公開され、OSVにマルウェアとして登録された。13件はインストール時に `web.archive.org` を経由して外部サーバーのスクリプトを取得し、そのまま `node` に流し込んで実行する。11件は本物と同じ版番号22.2.1を名乗っていた。
</callout>

#### なぜ重要か
- 通信先がInternet Archiveに見えるため、評判の良いドメインを許可しているだけの出口制御では止められない。
- 取得するコードは固定されておらず、実行のたびに中身が変わりうる。パッケージ自体を調べても実体が分からない。
- 1件は本物のAngular CLIを丸ごとコピーし、依存先のMCPパッケージだけを攻撃者のものに差し替える手口だった。
- AIのコーディングエージェントが、エラーやREADMEから推測した名前をそのままインストールすると、同じ穴に落ちる。

#### どう使うか
1. ロックファイルやCIキャッシュを、パッケージ名ではなく配布元の文字列で検索する。
2. CIでは既定でライフサイクルスクリプトを止め、必要なパッケージだけ許可する。
3. 社内レジストリやプロキシで、使ってよいスコープを許可リストで管理する。
```bash
# 配布元の文字列で検索（名前は変わっても配布元は残りやすい）
grep -rnE "gitflic\.ru|hellscripter|web\.archive\.org/web/https" \
  package-lock.json pnpm-lock.yaml yarn.lock node_modules/.package-lock.json 2>/dev/null

# CIではスクリプトを止めてインストール
npm ci --ignore-scripts
```
- 2-1のようにimport時に発動する例もあるため、`--ignore-scripts` は万能ではない点も合わせて押さえておく。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- Angularで業務アプリを作る受託開発会社が、案件テンプレートのCI設定を `npm ci --ignore-scripts` とスコープ許可リストに統一し、メンバーの打ち間違いによる感染を防ぐ。
	- コーディングエージェントを導入した開発チームが、エージェントに新しい依存を追加させるときは人の承認を必須にし、推測で入れたパッケージを実行前に止める。
</callout>

## ☁️ クラウド / インフラ / DevOps {color="orange"}

### 3-1 Kubernetesのノードswapで、エージェント用サンドボックスの密度が最大3倍に

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Kubernetes公式ブログが、ローカルNVMe SSDをswapに使ったときのベンチマークを公開した。gVisorで隔離したPythonサンドボックスは1ノード80個から240個に、gVisorのヘッドレスChromeは80個から160個に増えた。なお、ノードswapの機能自体はv1.34でGA済みで、今回の新情報は実測結果である。
</callout>

#### なぜ重要か
- AIエージェントの実行環境は、起動時に大量のメモリを使い、その後は指示待ちで遊ぶことが多い。遊んでいるメモリをSSDへ逃がせば、同じノードに多く載せられる。
- Linuxカーネルのビルドでは、メモリ上限を600MBから300MBに半減しても遅くならなかった。ただし200MBまで絞ると40%以上遅くなり、**swapは常用メモリの代わりではなく、急な増加への保険**と位置づけられている。
- ピーク密度での遅延増は主にCPUの取り合いが原因で、swapのI/Oではなかったと説明している。

#### どう使うか
1. cgroup v2のノードで、kubeletのswap設定を有効にする。
2. swap先は高速なローカルSSDにする（GKEではLocal SSDを使うNode Memory Swapが用意されている）。
3. 対象のPodはBurstable QoSにし、memoryのlimitsをrequestsより大きくする。
4. 目標の遅延を決め、ピークより低い密度で運用する。
```yaml
kind: KubeletConfiguration
apiVersion: kubelet.config.k8s.io/v1beta1
failSwapOn: false
memorySwap:
  swapBehavior: LimitedSwap
```
- 必要環境：Kubernetes v1.34以降、cgroup v2、ローカルNVMe SSD

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- コード実行サンドボックスを提供するAI SaaSが、同じノード数で同時セッション数を増やし、利用者1人あたりのインフラ費を下げる。
	- 社内CIを自前で運用するチームが、ビルド用Podのメモリ上限を下げて同時ジョブ数を増やし、待ち時間を短くする。
</callout>

### 3-2 AWS Private CA、証明書の中身まで記録する発行ログをCloudTrailに追加

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	AWS Private CAが、証明書を発行するたびに新しいCloudTrailイベント `IssueCertificateDetails` を記録するようになった。署名前の証明書の全フィールド、発行したCA、依頼者、署名の成否が入る。設定は不要で、追加費用は通常のCloudTrail料金だけだ。
</callout>

#### なぜ重要か
- これまでの `IssueCertificate` のログは「API呼び出しが成功した」ことしか分からず、証明書の中身や署名前の失敗は残らなかった。
- 名前制約違反など、**署名前に失敗した発行も理由つきで記録**されるため、設定ミスの調査がしやすくなる。
- 証明書の棚卸しや、署名アルゴリズムの移行（ポスト量子暗号への切り替えなど）の進み具合を追える。

#### どう使うか
1. CloudTrailで新イベントが届いているかを確認する。
2. EventBridgeで失敗した発行を検知し、担当者に通知する。
3. Athenaで定期的に集計し、有効期限や署名アルゴリズム別の証明書一覧を作る。
```bash
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=IssueCertificateDetails \
  --max-results 5
```
- 複数アカウント構成では、イベントはCAを持つアカウントに届く。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 社内PKIを運用する金融機関の情報システム部が、監査で求められる「誰がどの証明書を発行したか」の台帳を手作業ではなくCloudTrailから自動生成する。
	- IoT機器メーカーが、デバイス証明書の発行失敗をリアルタイムに検知し、製造ラインでの書き込み不良を早く見つける。
</callout>

### 3-3 Clockwork.io、GPU障害からの復旧を速める「TorchSnap」を発表、3,100万ドルを調達

	GPUクラスタの効率化ソフトを手がける米国の `Clockwork.io` が、3,100万ドルの資金調達と新機能「TorchSnap」を発表した。TorchSnapは分散推論ワークロードを複数ノードまとめてスナップショットし、コードを変えずに中断した地点から再開できるようにする。累計調達額は7,300万ドルになった。
</callout>

#### なぜ重要か
- 数千基のGPUを使う環境では、ハードウェア障害が毎日のように起きる。同社によると、保存した状態からの復旧に最大90分かかり、その間は正常なGPUも止まる。
- 既存のネットワーク障害の迂回（LinkPass）とGPU移行（TorchPass）に、スナップショットを加えた3層構成になった。
- 「障害への強さは学習だけでなく推論の問題にもなった」という指摘が出ており、推論基盤の可用性設計が重要になっている。
- LinkedInはLinkPassを全GPUに導入し、毎月数千GPU時間の停止をなくしたと紹介されている。

#### どう使うか
1. 自社のGPUクラスタで、障害1回あたりの復旧時間と、その間に遊んだGPU時間を計測する。
2. チェックポイントの間隔と保存先の速度を見直し、失う作業量を見積もる。
3. Together AIなど、TorchPassを提供するクラウドで効果を試してから自社導入を判断する。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 自社GPUで推論サービスを動かすAIスタートアップが、障害時の停止時間を減らしてSLAを守り、予備GPUの台数を減らす。
	- GPUを貸し出すネオクラウド事業者が、障害耐性ソフトを付加価値として提供し、大口顧客との契約で可用性を差別化する。
