## 🤖 AI / LLM / エージェント {color="purple"}

### 1-1 Google、自己改善エージェントの「テスト暗記」を抑えるRRSIを発表

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Google Cloud AI Researchらが、エージェントのハーネス（プロンプト、ツール、メモリなど）を自動改良するときの過学習を抑える手法「RRSI」を示した。モデルは凍結したまま、編集数の上限や批評役によって「ベンチマーク専用の改造」を弾く。論文は9月にarXivへ投稿済みで、10/4にThe Decoderが解説した。
</callout>

#### なぜ重要か
- 自動改良したハーネスは、改良に使ったタスクだけ得点が上がり、未知のタスクでは伸びないことが多い。
- RRSIは未知の5ベンチマークで**最大4.7ポイント改善**し、未正則化の自動改良よりトークン消費を約30%減らした。
- 評価セットの得点だけで採否を決める社内のプロンプト改善にも、同じ落とし穴がある。

#### どう使うか
1. 社内エージェントの評価セットを「改良用」と「検証用」に分け、検証用は改良ループに見せない。
2. 1回の改良で入れる変更数に上限を設け、ラウンドが進むほど小さくする。
3. 変更差分にタスク名や答えの直書きがないかを、別のLLMかレビューで確認してから評価に回す。
4. 得点の伸びがノイズ幅以内なら採用せず、コスト増には相応の得点増を求める。
- 実装はGitHub（google-research/rrsi）で公開されている。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- サポートAIを運用するチームが、FAQ評価セットへの過適合を防ぎ、新しい問い合わせ種別でも回答品質が落ちない改善サイクルを作る。
	- 社内コーディングエージェントの設定を自動チューニングする際、トークン費の増加を抑えつつ未知のリポジトリでの成功率を確かめる。
</callout>

### 1-2 Aleph Alpha、英独特化のオープンウェイトモデル「Kolibri」を公開

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	独Aleph Alphaが、英独バイリンガルのMoEモデル「Kolibri」をApache 2.0で公開した。総パラメータ78B、稼働は約3Bで、最大100万トークンの文脈に対応する。公開は10/3（ドイツ統一の日）で24時間枠の直前だが、dpaが10/4に報じたため週末分として例外的に採用した。
</callout>

#### なぜ重要か
- 稼働パラメータが約3Bと小さく、データを外部に出さずにオンプレで動かしやすい。
- 根拠が文書にないときは「分からない」と答えるよう訓練されており、AA-Omniscienceで44%の項目を誤答せず棄権した（同社発表）。
- 推論の強さを none／low／medium／high の4段階で切り替えられ、コストと品質を調整できる。

#### どう使うか
1. Hugging Faceで Aleph-Alpha/Kolibri-1 を取得する（Apache 2.0）。
2. vLLMプラグインを含む aleph-alpha-inference を入れて起動する。

```bash
pip install "aleph-alpha-inference>=1.0"
vllm serve Aleph-Alpha/Kolibri-1 --kv-cache-dtype fp8 \
  --reasoning-parser kolibri1 \
  --tool-call-parser kolibri1 \
  --enable-auto-tool-choice
```

3. 262,144トークンを超える文脈を使う場合は、公式ブログに載っている追加オプションを指定する。
- 推奨サンプリングは temperature=1.0、top_p=0.97、top_k=128（公式ブログ）。
- 日本語性能は公表されていないため、自社データでの検証が必要。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- ドイツ拠点を持つ製造業が、独語の仕様書や規制文書の要約・Q&Aを社内GPUで処理し、機密データを外部APIに送らずに済ませる。
	- 規制業界向けRAGで「根拠がなければ答えない」挙動を比較評価するときのベースラインにする。
</callout>

### 2-1 jpm：Claude Codeが全行を書いたRust製JSパッケージマネージャ

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Rust製で約2MBの単一バイナリのJavaScriptパッケージマネージャ「jpm」が、Show HNで公開された。作者のJT Turner氏が方針を決め、コードはClaude Code（Claude Opus 5.5）が全行を書いたと説明している。既存のnpm・pnpm・yarn・bunのロックファイルを取り込んで移行できる。
</callout>

#### なぜ重要か
- 依存パッケージのインストールスクリプトは、**承認するまで実行されない**。npmマルウェアの典型的な侵入経路を既定で塞ぐ設計だ。
- 公開から1日未満の新バージョンは選ばない（min-release-age）。乗っ取られたリリースがすぐ混入するのを防ぐ。
- 作者のベンチマークでは、GitHub CIでのnuxtのコールドインストールが1.22秒（npmは18.54秒）だった。
- AIが書いたコードを外部のテストスイート（Wycheproof、各パッケージマネージャのテスト）で検証する進め方そのものも参考になる。

#### どう使うか
1. 検証用ブランチでインストールし、既存のロックファイルから jpm.lock を作る。

```bash
curl -fsSL https://getjpm.sh | sh
cd your-project
jpm install   # package-lock.json / pnpm-lock.yaml / yarn.lock / bun.lock を読み jpm.lock を生成
```

2. CIでは、jpm.lock をコミットするまで旧ロックファイルのまま動く。

```bash
jpm ci
```

3. インストールスクリプトが必要なパッケージだけ jpm approve で承認する（詳細は公式の docs/install-scripts.md）。
- 公開されたばかりのツールなので、本番CIを切り替える前にビルド成果物の差分を確認する。
- 承認したスクリプトは自分の権限で動く。サンドボックスではない点に注意する。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- フロントエンド組織が、CIのインストール時間とキャッシュ容量を既存ツールと比較測定し、ビルド待ち時間の短縮効果を数字で示す。
	- サプライチェーン対策として「インストールスクリプトの承認制」「新版は1日待つ」を社内標準にするかどうかを、jpmで小さく試してから判断する。
</callout>

### 2-2 Obelisk 0.42：耐久ワークフロー上のエージェントと多層サンドボックス

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	耐久ワークフロー基盤Obeliskのバージョン0.42が公開された。AIが生成したコードを、レビューできる権限ポリシーの内側で動かす仕組みを強化している。JavaScriptをネイティブV8で動かすオプションと、Linux VM上で動くアクティビティ（実験的）も加わった。
</callout>

#### なぜ重要か
- 設定が server.toml・app.toml・deployment.toml に分かれ、実効権限はその共通部分になる。エージェントが広い権限を求めると、app.toml の小さな差分としてレビューに上がる。
- シークレットは既定でネットワーク境界で差し込まれ、コンポーネントのコードからは値が見えない。
- 726イベントの会話の再生が、Boa WASMの3.17秒から**V8では128ミリ秒（約25倍速）**に縮んだ（同プロジェクトの計測）。

#### どう使うか
1. 0.41からの更新には破壊的変更がある。公式の移行ガイドに沿って、設定を3ファイルに分ける。
2. V8を試すときは、サーバー起動時に環境変数で切り替える（既定はBoa）。

```bash
export OBELISK_JS_RUNTIME=v8
```

3. ポリシーの不足を検出し、--fix で雛形を作ってからレビューする。

```bash
obelisk deployment verify --fix
```

- crates.ioへの公開は終了したため、cargo install では新版を入手できない。
- コマンド deployment get は deployment pull に変わった。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- AIにワークフローコードを書かせる開発チームが、外部APIの許可ホストや使えるシークレットを app.toml で明示し、承認の流れを監査できる形にする。
	- 人の承認待ちが長い業務エージェント（稟議や問い合わせ対応）を、VMを常駐させずに中断・再開できる形で運用する。
</callout>

### 3-1 Citrix NetScalerのSAML機能に新ゼロデイ、9月更新済みの機器も再対応が必要

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	CitrixがNetScaler ADC／Gatewayの脆弱性CVE-2026-88779の修正版を緊急公開した。SAMLのSPまたはIdPとして設定された機器が対象で、標的型攻撃によるDoSが確認されている。研究者からは、リモートコード実行の可能性を示す観測も報告されている。
</callout>

#### なぜ重要か
- CVSS v4.0は8.7。CISAは既知の悪用脆弱性（KEV）に追加し、米連邦機関に10月7日までの対応を求めた。
- 先に公開されたCVE-2026-88771〜88778の修正版を入れた機器でも、条件に当てはまれば**再度のアップグレードが必要**になる。
- Citrixは影響をDoSと説明する一方、パッチ適用済みのハニーポットでマルウェアが動いたとの報告もある（Kevin Beaumont氏、BleepingComputer経由）。

#### どう使うか
1. 設定にSAML関連のエントリがあるかを確認する。

```bash
# 保存済み設定を検索する例（どちらかが見つかれば対象）
grep -E "add authentication (samlAction|samlIdPProfile)" /nsconfig/ns.conf
```

2. 該当する場合は、次のビルド以降へ更新する。
	- 14.1：14.1-73.41 以降
	- 13.1：13.1-64.28 以降
	- 14.1-FIPS：14.1-73.41 FIPS 以降
	- 13.1-FIPS／NDcPP：13.1-37.282 以降
3. 予期しない再起動や nsaaad のクラッシュ履歴、不審な認証ユーザー名がないかをログで確認する。
- Citrix管理のクラウドサービスはCitrix側で更新される。対象は顧客が管理する機器。

### 3-2 「ハード予算上限を既定に」：エージェント時代の課金暴走対策

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Simon Willison氏が、従量課金のサービスやAPIには「上限を超えたら止める」ハードな予算上限が既定で必要だと提言した。警告メールだけのソフト上限では、寝ている間の暴走課金を防げないという主張だ。紹介されたAWSの支出上限（9/16発表）とGoogle CloudのSpend Caps（7月）は、機能としては24時間以内の新発表ではない。
</callout>

#### なぜ重要か
- コーディングエージェントのおかげで、課金を伴うコードを誰でも簡単に動かせるようになった。その分、暴走時の請求リスクも広がっている。
- AWSの支出上限は、上限に達するとそのプロジェクトをその月は一時停止する仕組みだ。ただし現時点では**一部の顧客への限定提供**とされる。
- 同氏は、エージェント自身が「ハード上限のあるサービス」を勧めるようになるべきだと述べている。

#### どう使うか
1. 従量課金のクラウド、LLM API、SaaSを洗い出し、ハード上限の有無を一覧にする。
2. ハード上限があるサービスでは有効にする（AWSの新しい支出上限、Google CloudのSpend Caps など）。
3. 上限機能がないAPIは、アプリ側で月間コストを積算し、超えたら呼び出しを止める。

```python
# 例：LLM呼び出しの前に月間予算を確認し、超過なら止める（警告ではなくハード停止）
MONTHLY_BUDGET_USD = 50.0

def guarded_call(estimated_cost_usd, spent_this_month_usd, call):
    if spent_this_month_usd + estimated_cost_usd > MONTHLY_BUDGET_USD:
        raise RuntimeError("monthly budget cap reached")
    return call()
```

- 本番で止めたくないサービスは、上限の解除を明示的なオプトインにし、責任者を決めておく。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- AIエージェントの試作を社員に許可する情シスが、検証用アカウントにハード上限を必須とし、想定外の高額請求を防ぐ。
	- 受託開発会社が、顧客向けPoC環境の契約に「月額上限で自動停止」を盛り込み、課金トラブルのリスクを見積もりから外す。
</callout>

### 4-1 米政権、AI政策の統括組織「Super Intelligence Force」を発足

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	トランプ大統領が10/4（米国時間の日曜朝）、AI政策を調整するタスクフォース「Super Intelligence Force」の発足を発表した。国家情報長官のJay Clayton氏が率い、FTC委員長のAndrew Ferguson氏らが加わる。先週ホワイトハウスで主要AI企業が署名した自主的な安全基準に続く動きだ。
</callout>

#### なぜ重要か
- WSJの報道として、タスクフォースは**120日以内にAIのリスクと機会に関する報告書**をまとめるとされる（TechCrunch経由）。
- 憲章には、SI（超知能）を使った脅威への対応と、過剰規制の防止の両方が盛り込まれていると報じられた。
- 主要AI企業が合意した自主基準には、社内評価、外部監査、取締役会のレビューを含む「4層の統制と監査」がある（CBS News）。

#### どう使うか
1. 米国の主要AIモデルやAPIを使う事業では、今後120日の報告書と規制方針を監視の対象に加える。
2. 自社のAIガバナンスを「社内評価・外部監査・取締役会のレビュー」の3点で棚卸しし、取引先から同等の説明を求められても答えられるようにする。
- 自主基準は法的拘束力のない合意で、現時点で日本企業に直接の義務は生じない。

### 4-2 Google、OSSのバグ報奨金を一時停止：AI生成の無効報告が急増

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Googleが、OSS VRP（オープンソース脆弱性報奨金プログラム）での製品脆弱性の新規受付を止めた。理由は自動生成された報告の急増で、その大半が無効だったと説明している。停止は10/1付で、TechCrunchが10/4（米国時間）に報じた。
</callout>

#### なぜ重要か
- Googleは2027年第1四半期に続報を出すとしており、**再開日は決まっていない**。
- サプライチェーン関連の報告と、10/1より前に提出された報告は停止の対象外。一部のGoogle Cloudリポジトリの問題はCloud VRPで受け付ける（Tom's Hardware）。
- AIでバグ探しのコストが下がった結果、メンテナが「幻覚」報告の検証に追われる構図が業界全体に広がっている。

#### どう使うか
1. 自社で脆弱性の受付窓口やバグバウンティを運営しているなら、再現手順とPoCを必須にし、AI利用の申告欄を設ける。
2. 受付量に上限を設け、一次トリアージを自動化して、人の確認を本物らしい候補に集中させる。
3. 自社OSSの SECURITY.md に、受け付ける報告の条件を書いておく。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- バグバウンティを運営するSaaS企業のセキュリティチームが、AI生成の低品質報告を一次ふるい分けし、トリアージ工数を減らす。
	- OSSを公開している企業が、SECURITY.mdと報告テンプレートを整え、メンテナの対応負荷を抑える。
</callout>
