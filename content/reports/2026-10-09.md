### 1-1 Google、企業向け「Geminiエージェント」を発表

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Google CloudはGemini at Work 2026で、**目標（objectives）を渡すと計画・スキル／ツール利用・社内システム接続まで行う統合エージェント**を発表した。まずは企業向けに提供し、消費者向けは後続とする。モデルは既定で最適なものに振り分け、AnthropicのClaudeなど第三者モデルも選べる。
</callout>

#### なぜ重要か
- 単なるチャットではなく、WorkspaceやMicrosoft 365、Slack、Jira、Git、BigQuery、Snowflakeなどへ接続して成果物を返す設計だ。
- エージェント自身がWorkspaceアカウント（メールやカレンダー文脈）を持ち、操作は人ではなくエージェント名義の監査ログとして残る。
- マルチモデルのオーケストレーション、スマートルーティング、リアルタイムの利用上限など、コスト制御の仕組みも同時に示された。
- 早期検証にはOn、Shopify、PayPalなどが参加したと報じられている。

#### どう使うか
1. Gemini Enterpriseの契約と管理者設定で、エージェント機能の提供可否とモデル選択（Claude含む）を確認する。
2. 「週次レポート作成」「特定フォルダの要約と共有」など、承認フローと接続先がはっきりした業務から小さく試す。
3. tasks inboxで思考過程・サブエージェント・進捗を追い、監査ログの残し方を情シスと合意する。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 営業企画が、CRMとスライド置き場をつなぎ「競合比較メモを月曜朝までに作る」目標をエージェントに渡し、定例準備の時間を減らす。
	- 情シスが、第三者モデル選択と利用上限を先に決め、部門ごとのPoCを同じガバナンスの下で回す。
</callout>

### 1-2 JetBrains、コーディングエージェント向け「Mellum2.1」を公開

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	JetBrainsは、12B MoE（稼働2.5B）のオープンモデル**Mellum2.1**をApache 2.0で公開した。アーキテクチャはMellum2と同じだが、数百万回のサンドボックスRLにより、リポジトリの探索・ファイル編集・変更の自己検証ができるようになった。Hugging Faceで入手でき、GGUFやvLLM向けMTPヘッドは近日公開予定。
</callout>

#### なぜ重要か
- 同社評価では、SWE-bench VerifiedがMellum2の2.0から**47.0**へ上がった（同一のPiハーネス）。
- LiveCodeBench v6で82.0、HumanEval+で91.5など、同クラスのオープンモデル比較で上位に入る指標もある。
- 高負荷時のトークン供給はQwen3.5-9Bの約2倍、単一リクエストではMTPで約1.6倍速いと説明する。
- コードを外に出せない環境で、ローカル／自社インフラのサブエージェントとして使える選択肢が増える。

#### どう使うか
1. Hugging Faceから `Mellum2.1-12B-A2.5B-Thinking` を取得し、社内の小さなバグ修正タスクで精度と速度を測る。
2. 司令塔は上位クラウドモデル、リポジトリ内の調査・パッチ案はMellum2.1、という二段構成を試す。
3. GGUF公開後はOllama等でのローカル検証も計画に入れる。

```bash
# 例: Hugging Face Hubから取得（実IDはカードを確認）
huggingface-cli download JetBrains/Mellum2.1-12B-A2.5B-Thinking
```

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 受託開発会社が、顧客コードを扱う修正作業だけ自社GPU上のMellum2.1に限定し、機密要件を満たしながらエージェント支援を続ける。
	- プロダクト開発が、CIで落ちたテストの原因特定と修正案作成をサブエージェントに任せ、レビューだけ人が行う。
</callout>

## 🌐 Web / フルスタック開発 {color="blue"}

### 2-1 GitHub、Draft PRもユーザーあたりの上限に含められるように

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	GitHubは、リポジトリの**プルリクエスト上限設定にDraft PRも含められる**ようにした。これまで下書きは上限外だったため、制限を回避して大量のDraftを開く抜け道があった。通知やCIの浪費を抑えるための変更だ。
</callout>

#### なぜ重要か
- OSSや公開リポジトリでは、低品質な貢献やスパムがDraft経由で増えるケースがある。
- DraftもCIを動かす設定だと、コストとキューの混雑に直結する。
- メンテナーが「通常PRだけ制限」では防げなかった行為を、設定一つで抑えられる。

#### どう使うか
1. リポジトリのPR制限設定を開き、Draftを上限に含めるオプションを有効にする。
2. 正当なDraft運用（大きな機能の分割レビューなど）がある場合は、上限値を少し余裕を持たせる。
3. コミュニティに、Draft乱用への対応方針を短く告知する。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 人気OSSのメンテナーが、スパムDraftによるCI課金と通知疲れを減らし、本番レビューに集中する。
</callout>

### 2-2 GitHub、Triage権限でもPRをアーカイブ可能に

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	**Triage以上の権限**でPRのアーカイブ／解除ができるようになった。以前は管理者のみだった。アーカイブするとPRは閉じられ、会話は読み取り専用になり、新規コメントやリアクション、自動コメントも止まる。公開ビューからは隠れ、管理者には見える。
</callout>

#### なぜ重要か
- 信頼できるトリアージ担当に、コード変更権限を渡さずモデレーションを委任できる。
- スパム・重複・放置PRの整理が、管理者の手を借りずに回る。
- 解除しても自動では再オープンされないため、誤操作後の扱いを運用で決めておく必要がある。

#### どう使うか
1. トリアージ担当のロール割り当てを確認し、アーカイブ手順を短いランブックにする。
2. 「スパム／重複／3か月放置」など、アーカイブ基準をIssueテンプレかREADMEに書いておく。
3. 誤アーカイブ時は管理者またはトリアージが解除し、必要なら新規PRで再開する。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 社内OSS推進チームが、コミュニティモデレーターにTriageを渡し、管理者は権限変更とリリースに専念する。
</callout>

### 2-3 Vite 8.3.4：bundled-devのacceptExportsとpreload／HMR修正

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Vite 8.3.4が公開された（2026-10-08）。bundled-devで `import.meta.hot.acceptExports` が使えるようになり、chunkImportMap利用時のpreload、飛行中スタイルシート待ち、HMR既定値の破壊、開発サーバ再起動の取りこぼしなど複数の不具合が直った。パッチリリースだが、Vite 8系を本番・開発で使っているチーム向けの実務アップデートだ。
</callout>

#### なぜ重要か
- NextやNuxt以外のViteベースSPA／ライブラリ開発では、HMRとpreloadの不具合が開発体験と本番の初期表示に効く。
- bundled-dev利用時のホット更新まわりが前進している。
- メジャー機能追加ではないため、影響範囲を確認したうえで上げやすい。

#### どう使うか
1. 依存を8.3.4に上げ、開発サーバのHMRと本番ビルドのpreloadを回帰確認する。
2. `base` がルート以外、またはchunkImportMapを使っている場合は、特にアセットpreloadを重点確認する。

```bash
npm install vite@8.3.4
npm run dev
npm run build
```

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- フロントエンド基盤チームが、週次の依存更新に8.3.4を含め、開発中のHMR不具合チケットをまとめて閉じる。
</callout>

### 3-1 AWS DevOps Agent、プライベート網のリリース管理連携に対応

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	AWS SDK for Go v2の2026-10-08リリースで、**DevOps Agentのリリース管理アソシエーションがプライベートネットワーク経由**に対応した。GitHub／GitLab連携に `releaseManagementAssociationId` が付き、Release-readiness reviewやRelease TestingがVPC内リソースへ到達しやすくなる。
</callout>

#### なぜ重要か
- 本番前のゲートやテスト対象が閉域にある企業では、エージェントがインターネット経路だけだと検証できない。
- リリース判定エージェントを、既存のプライベートCI／検証環境に近づけられる。
- SDK経由での早期利用が可能になり、IaCや自作ツールからの組み込みが進む。

#### どう使うか
1. DevOps Agentのドキュメントで、プライベートアクセスに必要なネットワーク前提（VPCエンドポイント等）を確認する。
2. GitHub／GitLabアソシエーション作成時に、新しいリリース管理IDを扱うコードパスを試す。
3. リリース判定ジョブが、本当にVPC内のステージングへ届くかを小さく検証する。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**

</callout>

### 3-2 CloudFormation、ForceRollbackでロールバックを完了可能に

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	同じSDKリリースで、CloudFormationに**ForceRollback**が加わった。`ContinueUpdateRollback` でオプトインでき、個別リソースが元に戻せなくてもロールバックを完了させ、失敗したリソースはスキップとして記録する。
</callout>

#### なぜ重要か
- `UPDATE_ROLLBACK_FAILED` でスタックが長時間操作不能になる事態を、意図的に前進させられる。
- スキップしたリソースはテンプレートと不整合になり得るため、**次の更新前に必ず整合させる**運用が必須だ。
- 既存の `resources-to-skip` 運用と組み合わせ、障害時の復旧手順を短くできる。

#### どう使うか
1. 検証用スタックで意図的にロールバック失敗を起こし、ForceRollbackの挙動とイベント記録を確認する。
2. 本番ランブックに「スキップした論理IDの棚卸し→手動修復→次の更新」を追記する。
3. CLI／SDKを最新にし、ContinueUpdateRollbackの新パラメータを叩ける状態にする。

```bash
aws cloudformation continue-update-rollback \
  --stack-name my-stack \
  --resources-to-skip LogicalIdThatCannotRevert
# ForceRollback はコンソール／APIの新オプションとして提供（SDK v1.82.0系）。詳細はAPIリファレンスを確認。
```

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- SREが、深夜の失敗更新でスタックがロックされたとき、ForceRollbackでまず操作可能状態に戻し、翌朝に不整合リソースを計画的に直す。
</callout>
