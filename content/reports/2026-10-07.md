### 1-1 Mistral、1兆パラメータの「Mistral Large 4」をプレビュー公開

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	仏Mistralが、総パラメータ1兆・稼働49BのマルチモーダルMoE「Mistral Large 4」のプレビューを公開した。Mistral StudioのAPIで今日から試せて、**重みは今月末までに公開**する予定だ。強化学習はまだ続いており、ベンチマークは暫定値とされている。
</callout>

#### なぜ重要か
- 米国・欧州発のオープンウェイトでは最大級になる。同社は欧州の自社データセンターで、Grace Blackwell GPU 3,800基を使いゼロから学習したと説明している。
- 同社発表ではDeepSWE v1.1が61.7%、Terminal-Bench 4が28.3%。コーディングでは中国系の最上位モデルと並ぶ水準をうたう。
- サイバー分野を前面に出しており、Cybenchは93%。閉じたモデルが拒否しがちな脆弱性の再現作業も、自社環境で実行できる点を強調している。
- 160以上の言語で学習し、EUの全公用語を含む。欧州域内だけで完結する提供リージョンも用意する。

#### どう使うか
1. Mistral StudioでAPIキーを発行し、プレビューAPIで自社の評価セット（コード修正・文書読解・画像の位置特定など）を回す。
2. 重みの公開後、自社GPUやプライベートクラウドで動かす場合の必要メモリとライセンス条件を確認する。
3. 公開までに出る予定のアーキテクチャ詳細と追加ベンチマークを待ってから、本番採用を判断する。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 顧客データを国外に出せない金融・公共系のSIerが、重み公開後にオンプレで動かし、セキュリティ運用（マルウェア解析や検知ルール作成）の補助に使う。
	- 製造業の設計部門が、図面や点検写真の読み取りをプレビューAPIで試し、目視確認の工数削減を見積もる。
</callout>

### 1-2 Anthropic、サイバー検証プログラムを3段階に再編

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Anthropicが、審査済みのセキュリティ組織向けにサイバー関連の制限を緩める「Cyber Verification Program」を拡大した。Mythosを提供していたProject Glasswingと統合し、Defense・Red Team・Specializedの3段階に分けた。各段階でClaude Opus 5.5、Sonnet 5.5、Mythos 5.1を使える。
</callout>

#### なぜ重要か
- 一般提供のClaudeはサイバー作業の多くを止める設定だが、防御側は審査を通れば制限の少ない環境を使えるようになった。
- Defense Accessは企業のSOC、病院や自治体の水道などの重要インフラ、OSSメンテナー、実績のある個人研究者も対象。審査は数日を目安としている。
- 同社の評価では、Red Team Accessで**50課題中34件を完了**し、制限なしと同等だった。Defense Accessでは50件中46件が途中でブロックされた。
- 参加組織にはデータ保持が必要になる。ゼロデータ保持と両立する「Enterprise Frontier Safeguards」は今秋に提供予定だ。

#### どう使うか
1. 自社の用途（インシデント対応・マルウェア解析か、許可を得たペネトレーションテストか）を整理し、該当する段階を決める。
2. 公式ページの申請フォームから申し込み、求められるセキュリティ管理の証跡を用意する。
3. 承認後、管理者がワークスペースごとにアクセスを割り当てる。
- Claude Platform、Vertex AI、Microsoft Foundryで利用できる。Amazon BedrockはEFS対象の顧客に限られる。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 中堅企業の社内SOCがDefense Accessを取り、アラートの一次調査とマルウェア検体の解析をClaudeに任せて、夜間対応の待ち時間を減らす。
	- 診断会社がRed Team Accessで、許可済みの顧客環境に対する攻撃シナリオの作成と検証を効率化する。
</callout>

### 1-3 OpenAI Codex、Auto-reviewが無料に

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Codexで、サンドボックス外の操作の承認を別のレビュー役エージェントに任せる「Auto-review」が、ChatGPTアカウントでサインインした全員に無料で開放された。レビュー分の利用量がプランから差し引かれなくなった。機能自体は4月から提供済みで、今回の変更は料金面である。
</callout>

#### なぜ重要か
- 承認待ちが面倒で「フルアクセス」に切り替える運用が多かった。安全な設定のほうが高くつく状態が解消された。
- レビュー役は、外部への機密送信、認証情報の探索、セキュリティ設定の弱体化、取り返しのつかない削除などを止める。
- 拒否が3回続くか、直近50件で10回拒否されると、そのターンを中断する。言い換えで押し切られにくい作りだ。
- OpenAIは**セキュリティの保証ではない**と明記している。だまされる例も見つかっている。

#### どう使うか
1. アプリでは設定の「Permissions」でAuto-reviewを選ぶ。既定はオフ。
2. CLIや共有設定では `~/.codex/config.toml` に次を書く。
	```toml
	approval_policy = "on-request"
	approvals_reviewer = "auto_review"
	```
3. よく使う安全なコマンドは、`["pnpm", "run", "lint"]` のように狭いプレフィックスで許可し、レビュー件数そのものを減らす。
- 無料化の対象はChatGPTサインインの利用者。APIキー課金の扱いは発表に含まれていない。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 開発チームの共通設定（requirements.toml）でフルアクセスを禁止し、Auto-reviewを標準にして、エージェントの夜間バッチ作業を止めずに安全性を上げる。
	- 情報システム部門が、`~/.codex/sessions` に残るレビュー記録を月次で確認し、許可ルールの見直しに使う。
</callout>

## 🌐 Web / フルスタック開発 {color="blue"}

### 2-1 GitHub、スタックPRを正式提供

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	大きな変更を小さなPRに分けて積み上げ、個別にレビューしてまとめてマージできる「stacked pull requests」が、github.comの全プランで正式提供になった。正式版ではリベース時の承認の維持、署名付きコミットの再作成、マージキューでの一括処理が加わった。GitHub Enterprise Serverには今後のリリースで入る。
</callout>

#### なぜ重要か
- これまでスタック運用は外部ツール頼みだった。標準機能になり、レビューしやすいPRの粒度を保ちやすくなる。
- 未変更のスタックをmainに合わせてリベースしても、**承認が消えない**。古い承認を破棄する設定のリポジトリでも同じだ。
- スタックはマージキューに1つのマージグループとして入る。途中だけ取り込まれて壊れる事態を防げる。
- 利用リポジトリではマージされたコード量が9%増えたと、GitHubは説明している。

#### どう使うか
1. 大きな機能を「DBスキーマ→API→UI」のように依存順に分け、PRを積み上げる。
2. PR画面のヘッダーでスタック全体を確認し、`Shift`＋`J`／`K` で前後のPRに移動してレビューする。
3. CLIでは `gh stack` 拡張を使う。Git worktreeに対応した。
4. 自動化する場合は、`pull_request` Webhookの `stacked` アクションを受けてCIを分ける。
- スタックの自動マージは今後数週間で順次提供される。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 受託開発チームが、数千行になりがちな機能追加を3〜4本のスタックPRに分け、顧客側レビュアーの確認時間を短くする。
	- コーディングエージェントに作業単位ごとのPRを積ませ、人は上から順にレビューして、まとめてマージキューに流す。
</callout>

### 2-2 Vercel AI Gateway、確信度の低い判定だけ上位モデルに回す機能

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Vercel AI Gatewayが、分類や採点などの「判定」リクエストで、主モデルの確信度が設定値を下回ったときだけ別モデルに回す機能をベータで追加した。AI SDKの `decide` で使う。条件を書かないリクエストは従来どおり動く。
</callout>

#### なぜ重要か
- 安いモデルで大半をさばき、迷った案件だけ高性能モデルに回す構成を、アプリ側の分岐なしで組める。
- Choice（選択）とScore（採点）は確信度で、Boolean（はい・いいえ）は確率の範囲で切り替える。
- フォールバックが発動すると2段階分が課金される。しきい値の決め方がコストに直結する。

#### どう使うか
1. `providerOptions.gateway.models` に条件付きのフォールバックを1つ追加する。
	```typescript
	import { gateway } from '@ai-sdk/gateway';
	import { experimental_decide as decide } from 'ai';
	
	const result = await decide({
	  model: gateway.decisionModel('typesafe-ai/jev'),
	  state: 'I was charged twice and now the app will not load.',
	  questions: {
	    intent: {
	      type: 'choice',
	      instructions: 'Which team should handle this?',
	      criteria: { billing: 'Charges and refunds', technical: 'Bugs and outages' },
	    },
	  },
	  providerOptions: {
	    gateway: {
	      models: [{ model: 'openai/gpt-6-astra', when: { question: 'intent', confidenceBelow: 0.6 } }],
	    },
	  },
	});
	```
2. `question` を省くと、同じ種類のすべての質問に条件が効く。
3. 本番前に過去の問い合わせで、しきい値ごとのエスカレーション率と費用を測る。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- SaaSのサポート部門が、問い合わせの担当振り分けを軽量モデルで行い、確信度0.6未満だけ上位モデルに回して、誤振り分けとAI費用を同時に抑える。
	- 与信や不正検知の一次スクリーニングで、判断が割れる案件だけ上位モデルと人の確認に回す。
</callout>

## ☁️ クラウド / インフラ / DevOps {color="orange"}

### 3-1 AWS Certificate Manager、ACMEでの証明書発行がPrivateLink経由に対応

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	ACMのACME方式による公開TLS証明書の発行と更新を、AWS PrivateLink経由で行えるようになった。VPCインターフェースエンドポイントを作れば、インターネットに出ずにAWSネットワーク内で処理が完結する。全商用リージョンで使える。
</callout>

#### なぜ重要か
- インターネットへの出口を持たない閉域VPCでも、certbotなどの標準ACMEクライアントで証明書を自動更新できる。
- **ACMEクライアントの設定変更は不要**。プライベートDNSが既存のディレクトリURLをエンドポイントに向ける。
- 発行の操作はACMコンソール、CloudTrail、CloudWatchで追える。監査対応がしやすい。

#### どう使うか
1. ACMでマネージドACMEエンドポイントを作成する（既に使っていれば不要）。
2. VPCコンソール、AWS CLI、CloudFormationのいずれかで、ACM ACME向けのインターフェースエンドポイントを作り、プライベートDNSを有効にする。
3. 既存のACMEクライアントで更新を試し、CloudTrailに発行のイベントが残ることを確かめる。
- PrivateLinkのエンドポイント料金が別にかかる。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 金融・医療系の閉域システムを運用するチームが、NATやプロキシを開けずに証明書の自動更新を実現し、期限切れによる障害と監査指摘を減らす。
</callout>

### 3-2 AWS Batch、ジョブのメトリクスをCloudWatchに標準で出力

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	AWS Batchが、ジョブの状態遷移と所要時間のメトリクスを `AWS/Batch` 名前空間に自動で送るようになった。ジョブキュー名の次元で、投入・実行・成功・失敗の件数や、投入から実行開始までの時間が見える。Batchが使える全リージョンで有効だ。
</callout>

#### なぜ重要か
- これまではEventBridgeで状態変化を拾い、自前で集計する必要があった。**追加の仕組みなしで**キューの詰まりや失敗率を監視できる。
- 「投入から実行可能になるまでの時間」が取れるため、計算資源の不足を早く見つけられる。

#### どう使うか
1. どのメトリクスが出ているかをCLIで確認する。
	```bash
	aws cloudwatch list-metrics --namespace AWS/Batch
	```
2. 失敗件数と待ち時間にCloudWatchアラームを設定し、通知先を決める。
3. 自前の集計Lambdaなどがあれば、置き換えられるか検討する。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- 夜間に大量の集計・機械学習の前処理を回すデータチームが、キューの待ち時間アラームで朝の遅延を事前に検知し、計算環境の上限を調整する。
</callout>

### 3-3 Cloudflare WAF、F5 BIG-IPの悪用中の脆弱性を既定でブロック

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	CloudflareがWAFのマネージドルールに、F5 BIG-IPの認証不要ヒープオーバーフロー（CVE-2026-94127）の検知ルールを追加し、既定の動作をブロックにした。脆弱性自体は9/22に公表済みで、CISAの悪用確認済みリスト（KEV）にも入っている。今回の新情報はWAF側の対策だ。
</callout>

#### なぜ重要か
- BIG-IP APMをOAuth認可サーバーとして設定している場合、認証なしでリモートコード実行につながる。CVSS v3は9.8。
- OAuthクライアント・リソースサーバーとしてだけ使う構成は対象外とされる。
- WAFは**パッチの代わりにはならない**。Cloudflareを経由しない経路や社内からのアクセスは守れない。

#### どう使うか
1. BIG-IP APMでOAuth Authorization Serverプロファイルを使っているかを確認する。
2. 使っていれば、F5の告知（K000162605）に沿って修正版を適用する。
3. Cloudflareの前段にあるサイトでは、マネージドルールセットが有効で、該当ルールがブロックになっていることを確認する。
4. 同じリリースでコマンドインジェクションのベータ判定が本ルールに統合されたので、誤検知がないかログを見る。

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- リモートアクセス基盤にBIG-IPを使う企業の情シスが、パッチ適用までの間をWAFで補い、適用後もWAFルールを残して多層防御にする。
</callout>
