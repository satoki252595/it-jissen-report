### 1-1 Google、Gemini 4 Argonを段階公開

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Google DeepMindが次世代フロンティアモデル **Gemini 4 Argon** を発表した。当面はFairwind Program経由で信頼されたサイバー防衛者向けに限定公開し、広く開発者・企業へは段階的に拡大する。出力トークン上限は最大**100万トークン**まで拡張され、導入価格は入力$2／出力$10（100万トークンあたり）と案内されている。
</callout>

#### なぜ重要か
- DevDay翌日の発表で、安全面を優先した「能力はあるがすぐには一般開放しない」というフロンティア公開の型が明確になった
- ソフトウェア工学・法律／金融などのナレッジワーク、サイバー防衛に強いと位置づけられ、長時間ワークフロー向けの設計が前面に出ている
- 社内では大規模コードベース移行やメモリ最適化など、すでに実務利用が進んでいると説明されている

#### どう使うか
1. 一般API／Google AI Ultra向けの拡大時期を公式ブログとGoogle Cloudの案内で追う
2. サイバー防衛用途では、ガードレールなし公開は信頼された防衛者向けである点を前提に、利用ポリシーを設計する
3. 価格は導入期間後に入力$4／出力$20（100万トークンあたり）へ移行する旨が記載されているため、予算試算に反映する

必要環境:
- 現時点ではFairwind Program等の限定アクセスが前提
- 広範な開発者向けAPIは「近日」と案内され、日程は未確定

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- セキュリティチーム: 脆弱性発見・パッチ案作成のパイロットを、アクセス解放後に限定リポジトリで試す
	- プロダクト開発: 大規模リファクタやドメイン横断の調査タスク向けに、長出力トークンを前提としたプロンプト設計を先に整える
</callout>

### 1-2 OpenAI、協調的なモデル蒸留キャンペーンを遮断

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	OpenAIが、モデルの**保護済みreasoning（内部推論）**を抽出する協調キャンペーンを検知し遮断したと発表した。活動は7月初旬から観測され、高負荷のスパイク後に関連アカウント群を封じたと説明している。報道ではコアクラスタがMoonshot（Kimi）に結びつくとされているが、OpenAIは単一主体への断定を避けている。
</callout>

#### なぜ重要か
- 最終回答だけでなく内部reasoningの流出が、モデル能力の不正再現につながるリスクが具体化した
- アカウント取り締まりに加え、hidden reasoningの保護強化や第三者経由の遮断連携まで踏み込んでいる
- API利用者・代理店経由の利用でも、異常な抽出パターンが組織単位の制限対象になりうる

#### どう使うか
1. 企業契約では利用規約の蒸留禁止条項と監査ログの有無を再確認する
2. 自社プロキシ経由でLLMを使う場合、異常な高頻度・同型プロンプトの検知ルールを入れる
3. 第三者にreasoningログや中間出力を渡す設計があるなら、再配布リスクを見直す

<callout icon="💼" color="green_bg">

	- 法務・調達: ベンダー契約に蒸留・転用禁止と監査協力条項を明示し、インシデント時の連携手順を決めておく

### 2-1 Next.js September 2026 Security Release

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Next.jsが予定どおりセキュリティ修正を公開し、**v16.3.8（Active LTS）**と**v15.5.27（Maintenance LTS）**への更新を求めた。先送りされていたCritical／Highを含む複数件が対象で、Image OptimizationのSSRF、自己ホスト環境でのキャッシュポイズニング、開発サーバのMCPエンドポイント情報漏洩などが含まれる。
</callout>

#### なぜ重要か
- `images.remotePatterns` を設定している環境ではSSRF（CVE-2026-94483）の影響を受けうる
- 自己ホストのSSG／ISRではキャッシュポイズニングにより誤コンテンツ配信やDoSにつながりうる（Vercel上は対象外と明記）
- `next dev` のMCPエンドポイントは本番ではなく開発時のリスクだが、ソース断片の漏洩につながる

#### どう使うか
1. 直ちにパッチ版へ上げる

```bash
npm install next@15.5.27  # for 15.5
npm install next@16.3.8   # for 16.3
```

- Image Optimizationを使う場合は `images.remotePatterns` の許可範囲を最小化する
- 自己ホストでPages RouterのSSG／ISRを使うなら、キャッシュ挙動と再検証手順を確認する
- 開発サーバのMCPエンドポイントを外部公開していないかネットワーク設定を点検する

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- Webチーム: CIでNext.js版を固定し、セキュリティアドバイザリ公開当日に自動PRを出す運用にする
	- プラットフォーム担当: 自己ホストとVercelの影響範囲を分け、自己ホスト群を優先パッチ対象にする
</callout>

### 2-2 Cloudflare Monetization Gateway beta（HTTP 402）

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Cloudflareが **Monetization Gateway** をクローズドベータで公開した。ドメイン所有者がサイト／API／MCPツール／データセットへ、**HTTP 402 Payment Required** を使った従量課金をかけられる。決済はCoinbase x402 Facilitator経由でBase上のUSDC決済が案内されている。
</callout>

#### なぜ重要か
- エージェント交通が増える前提で、「登録＋月額」ではなくリクエスト単位の課金レールが実装レベルで揃い始めた
- AI Gatewayの推論課金やCeramicの検索、Stocktwitsのシグナル、API2PDFなど、本番利用例が同時に示された
- チェックアウトページや別決済APIなしで、HTTPレスポンス内で支払い指示を返せる

#### どう使うか
1. Cloudflare DashboardからMonetization Gatewayのアクセス申請を行う
2. 課金対象（URL／ヘッダ／クエリ）と価格ルールを定義する
3. エージェント側は402レスポンスの支払い指示に従って署名・決済し、リソースを再取得する
4. AI Gatewayで即時払いする場合の例:

```bash
curl -iX POST "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/ai/run" \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  --header "Payment-Method: x402" \
  --header "Content-Type: application/json" \
  --data '{"model":"z-ai/glm-4.7-flash","input":{"max_tokens":9001,"messages":[{"role":"user","content":"What is Cloudflare?"}]}}'
```

必要環境:
- Cloudflareアカウントと対象ドメイン／API
- ベータ参加承認（クローズド）
- エージェント側のx402対応ウォレット／クライアント

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- API事業: ドキュメントや相場シグナルをエージェント向け従量課金で公開し、従来のエンタープライズ契約と併用する
	- 社内プラットフォーム: 外部エージェントからの社内ナレッジAPIアクセスに、低額の従量課金と利用ログを付ける
</callout>

### 3-1 Cloudflare AI Gateway Auto Router（public beta）

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	AI Gatewayに **Auto Router** がpublic betaで入った。モデルを `cloudflare/auto` にすると、タスク分類と複雑さ推定に基づき十分な能力のモデルへ自動ルーティングする。社内OpenCode利用ではフロンティア単体比で最大約**30%**のコスト削減を報告している。
</callout>

#### なぜ重要か
- 利用者にモデル選定を任せず、ゲートウェイ側で品質と価格のトレードオフを取れる
- セッション中のキャッシュ破棄コストまで織り込み、無闇なモデル切替を抑える設計になっている
- ベータ期間中はAuto Router自体は無料と案内されている

#### どう使うか
1. AI Gatewayで利用可能なモデル群と認証情報を設定する
2. クライアントのモデル指定を `cloudflare/auto` に切り替える
3. ルーティング結果とコストをGatewayの分析で監視し、必要なら将来の `cloudflare/auto-best` 等のプロファイルを検討する

必要環境:

### 3-2 AWS CloudTrail Event Coverage

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	AWS CloudTrailに **Event Coverage** が追加された。アカウント／組織単位で、どのサービス・リソース種別のデータイベントが有効かを一覧し、未設定の抜けを見つけやすくする。ダッシュボードからデータイベント購読もできる。
</callout>

#### どう使うか
1. CloudTrailコンソールでEvent Coverageを開く
2. 組織全体の未カバー領域（例: 重要バケットのオブジェクトレベルログ）を洗い出す
3. ダッシュボードから不足分のデータイベントを有効化する
4. セキュリティ監視（SIEM／GuardDuty連携）の検知条件を合わせて更新する

### 3-3 Aurora PostgreSQLがIceberg／Parquetを直接クエリ

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	Amazon Aurora PostgreSQLが、S3上の **Apache Iceberg／Parquet** を既存のPostgreSQL構文で直接クエリできる機能を発表した。DuckDBがAurora内に組み込まれ、ETLで複製せず運用データとレイクデータを結合できる。対応はAurora PostgreSQL 17.11以降および18.6以降。
</callout>

#### なぜ重要か
- 逆ETLで履歴データを運用DBへ戻すパイプラインを減らせる
- AIエージェントが「今必要になったデータ」を事前複製なしで参照しやすくなる
- 追加料金はなく、増分のAuroraコンピュートとS3リクエスト課金のみと案内されている

#### どう使うか
1. Aurora PostgreSQLクラスタに `AuroraAnalytics` 機能付きIAMロールを付与する
2. 拡張を有効化し、外部テーブルを作成する

```sql
CREATE EXTENSION aurora_analytics;

CREATE FOREIGN TABLE transaction_history ()
SERVER aurora_analytics_server
OPTIONS (
    location 's3://<my-bucket>/finance/transaction_history.parquet',
    format 'parquet'
);
```

- 運用テーブルとUNION／JOINしてダッシュボードやエージェント用クエリを組む
- 低レイテンシが必要なら `CREATE TABLE AS SELECT` 等でホットデータをマテリアライズする

<callout icon="💼" color="green_bg">
	**ビジネス活用例**
	- データ基盤: 直近取引はAurora、過去数年はIcebergのまま、顧客サポート画面を単一SQLで出す
	- AIアプリ: エージェントが履歴照会するたびにETLを待たず、レイク参照をその場で実行する
</callout>

### 4-2 Restate、$20M Series Aでエージェント耐久実行を強化

<callout icon="📌" color="gray_bg">
	**何が新しいか**
	耐久ワークフロー基盤のRestateが、Singular主導で**$20MのSeries A**を調達した。RedpointとCapital One Venturesも参加。エージェントのような長時間・分岐の多い処理に耐久実行が必要だとして需要が拡大している、とTechCrunchが伝えている。

#### なぜ重要か

- 「失敗したら途中から再現可能に再開する」層が、エージェント本番化の共通インフラになりつつある

#### どう使うか
1. 自社エージェントで外部API呼び出しが多いなら、ステップ単位の耐久実行が必要か評価する
2. Temporal等既存基盤との比較軸を、レイテンシ・運用コスト・言語SDK・運用成熟度で整理する
3. 金融など厳密な再実行が必要な業務から、パイロット対象を絞る

	**ビジネス活用例**
	- エージェント基盤チーム: 請求・在庫更新など副作用のあるツール呼び出しを耐久ワークフローに載せる
	- スタートアップCTO: Temporal一択だった選定を見直し、コストと起動速度でRestateを比較候補に入れる
</callout>
